# ADR-0014: The page gets only the commands it calls

- **Status:** Accepted
- **Date:** 2026-11-08

## Context

A script injected into the WebView, by an HTML sink nobody has found yet or a
compromised frontend dependency, would hold the page's whole authority
(threat model B1, F9). That authority was wider than the page needs: with no
application manifest Tauri lets any window call every app command; the
capability granted `core:default` (menus, trays, new webviews, paths) and the
notification and updater plugins whole; `core_call` and `core_send` passed any
command name on to the core, the protocol's `shutdown` and `info` included,
and on either lane; account and folder arguments were plain strings; and the
setting that lifts the helpers' privilege cap could be turned on by one call.

The CSP and the absence of HTML sinks make injection unlikely; the question is
what one would get. The options were a second window or a scoped command per
feature (heavy for one window that uses everything it registers), or holding
each existing door to what the page actually uses.

## Decision

Hold each door to the page's own use, with one list behind each:

- **App commands.** build.rs reads the handler (`app_handler!` in lib.rs) and
  gives it to `tauri_build::AppManifest::commands`, so every app command is
  permissioned like a plugin's. `capabilities/default.json` grants the `main`
  window each one by name, and only the plugin calls the page makes (seventeen:
  the app version, event listen and unlisten, seven window actions,
  `dialog:allow-open`, three notification and three updater calls). Remote origins get nothing.
- **Core bridge.** `corecmd::COMMANDS` lists the 35 core commands the page
  sends, each with its lane (33 answered, 2 sent). `core_call` and `core_send`
  refuse anything else, and `dispatch` refuses it again.
- **Paths.** Account and folder arguments are typed at the boundary
  (`boundary.rs`): an `AccountPath` is a folder directly in a provider's
  folder under the accounts root, with a valid account name, neither it nor
  the provider's folder a link, junction or mount point, and resolving on
  disk to that folder under the root by the very name given; an `AbsPath` is
  absolute with no `.`, `..`, device or verbatim prefix or stream suffix.
  Every path argument of a core command, the app commands that write an
  account's files, use its credentials or widen trust, and those that may
  run the Codex CLI on an account take them (`OrEmpty` where the page may
  send none).
- **The cap.** `set_helpers_above_caller(true)` asks a native dialog in the
  window process, one at a time; a yes applies only if the setting did not
  change while the dialog was open, and a request that finds the cap lifted
  already writes nothing.

## Consequences

- An injected script can no longer reach a command the page does not call,
  stop the core, open windows or trays, or write outside account folders
  through the config editor.
- It can still do what the page does: start a session in any folder with any
  mode and type into it, which is code execution as the user. That is the
  app's purpose and stays a residual (threat model B1). Through such a
  session it can also lift the helper cap without the dialog: edit Luna's
  settings file, or drive the dialog with synthetic input as any program of
  the user's can. The dialog keeps the page's own call from doing it in one
  step; it is no boundary against code already running as the user.
- A new command needs its `allow-` line and its committed
  `permissions/autogenerated/<command>.toml` (build.rs writes it where a
  writable checkout builds; the read-only Linux check needs it committed).
  The `acl` tests in lib.rs (a mock app, run by the Linux check; a test exe
  on Windows cannot load the menu and tray code without the app manifest)
  and the core list's test in corecmd.rs fail until both lists agree.
- Read-only commands that run nothing and whose page callers may send an
  empty path (Claude defaults, saved titles, hooks state, worktree
  inspection) keep plain strings.
